# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
cargo build                       # build lib + all bins
cargo test                        # all integration tests (tests/*.rs)
cargo test --test models          # one test file
cargo test test_calibration_metrics   # one test by name (substring match)
cargo clippy --all-targets        # lint
cargo fmt                         # format (no rustfmt.toml; uses defaults)
```

Runnable binaries (`src/bin/`): `run_backtest` (simulated markets), `run_backtest_real` (real markets from CSV/JSON), `download_polymarket_history`, `capture_prices`, `weather_dashboard`, `kalshi_pilot` (real-money pilot, dry-run by default), `example_workflow`, `live_trading_example`. CLI flags are parsed by hand (see gotchas). Two real-data flows:

- **Real-data backtest:** `download_polymarket_history` → CSV → `run_backtest_real --markets <csv>`.
- **Forward calibration:** Polymarket purges price history shortly after a market resolves, so real entry prices only exist while markets are live. `capture_prices` (run daily; a launchd agent `com.polymarketweather.dailycapture` drives it via `scripts/daily_capture.sh`) snapshots every active weather market's price + model estimate to `data/captures.jsonl` and fills in outcomes as markets resolve. `weather_dashboard [--markets <csv>] --output dashboard.html` renders calibration (Brier / ECE / reliability) + the forward trading-strategy readout (edge threshold → fractional Kelly → compounding PnL, hit rate, per-venue/city/market-type breakdown, open book), fetching weather once per city into `data/weather_cache/` (`--refresh` re-fetches). `--markets` is optional: omit it to render the forward readout from captures alone. Strategy knobs: `--edge-threshold` / `--kelly-fraction` / `--max-position-pct` / `--bankroll`, plus filters `--sell-only`, `--min-price`, `--segment-lambda` and `--raw-edge`. **`--edge-threshold` defaults to 0.10 since 2026-08-17** in the dashboard AND the pilot (promotion of shrunk + edge ≥ 10%: it led its forward-since-freeze window at both checkpoints with the lead GROWING as n doubled — +26.4% vs the default's +11.0% at n=39 on 08-09, +32.7% vs +15.0% at n=77 at promotion — robust with and without SELL-only; `config::backtest_params().edge_threshold` stays 0.05 for the raw-edge backtest engine, where 10% was never the validated cut). Shrunk-edge is the DEFAULT since 2026-07-19 (`--raw-edge` restores raw disagreements; `--shrink-edge` is a legacy no-op): it led the A/B tracker every day of its two-week window (+5.0% ROI / 35% edge capture vs +2.2% / 11% raw at the 631-settled-trade checkpoint) and its walk-forward λ makes that lead out-of-sample by construction. λ is a per-venue through-origin regression of realized on claimed edge, fitted walk-forward on resolved lead ≥ 1 captures — lead ≤ 0 rows are excluded from the fit because their prices already embed the outcome. - **Distance-from-forecast (`--min-forecast-distance`, A/B candidate 2026-08-05, RETIRED 2026-08-23) — and the σ defect underneath it.** The 07-20 refit fixed the mean bias but the σ rescale (×1.32 Polymarket) OVER-widened: on realized highs recovered from winning buckets, post-refit z = (realized − forecast)/σ has **sd 0.78** with 82% of days inside ±1σ against the Normal's 68% (pre-refit sd 1.29, mean z −0.50 → +0.12). A too-wide σ flattens the posterior peak, so the buckets ADJACENT to the model's own forecast get under-priced and show large claimed edges that are just the model's excess spread. Splitting settled SELLs under the default config at 1.5 °C (captures through 08-04): far ≥ 1.5 °C realizes **+0.133/trade at 52% capture** (n=140), near < 1.5 °C realizes **−0.056 at −27%** (n=105). The cut is nearly ORTHOGONAL to `--min-price` (in the raw ≥5¢ SELL population both sides are almost entirely ≥ 10¢ — 288 near vs 252 far), so the price floor does not already capture it. As A/B rows: **shrunk + bucket ≥ 1.5 °C** gives 462 trades / +17.2% ROI / 126% capture and **stacked with SELL-only** 303 / +20.1% / 151% / 80% win, both against the default's 743 / +9.4% / 76% — and it keeps far more trades than `edge ≥ 10%` (462 vs 318) at comparable ROI, i.e. it removes bad trades rather than merely small ones. Markets where the axis is undefined (threshold shapes; the 7% of bucket captures predating `forecast_high`) pass the filter rather than being silently dropped, and rows are folded into the λ fit BEFORE the gate so a filtered config still learns from what it declines to trade. Threshold and axis were both chosen on that sample — **and the filter always treated a symptom, not the cause.** The cause was the over-wide σ, and the 2026-08-05 refit addressed it (σ ×0.8, bias +0.32/+0.04); since a refit only changes how FUTURE captures are priced, the numbers above are frozen under the old σ and the test was whether post-refit rows would pull the filter back to the default. **They did, and the rows were RETIRED 2026-08-23 on that pre-committed rule** — forward +30.4% · 75 and +31.9% · 67 SELL-only against the default's +32.3% · 73 on the identical window, i.e. parity or a shade behind, down from a 2.3× lead over the old default. So the σ fix priced the defect out and the filter has nothing left to remove; it is retired for SUCCEEDING as a diagnostic, unlike segment λ which was retired for trailing. `--min-forecast-distance` remains a functional CLI knob and the eligibility helper + tests stay, so re-freezing a row is cheap if a future σ change reopens the gap. The remaining σ half-step (the 08-05 fit wanted ×0.61/×0.68, capped to ×0.8 by `--sigma-floor`) is NOT indicated by this: it was the fallback for the rows failing to converge, and separately the k=1,2 σ tables are now mostly a fallback anyway since ensemble σ landed 08-09.
- **The daily-capture Action is the only source of forward data, and a missed day is permanent.** Polymarket purges price history shortly after a market resolves, so a day the workflow skips can never be backfilled — 2026-08-26 is a permanent hole (GitHub delivered the schedule five times in twenty minutes and gave none of them a runner: two `startup_failure`, two `failure`, one `cancelled`; the same class of outage as the Kalshi-zero window 08-13→08-18). Since 2026-08-30 the workflow carries a BACKUP cron 37 minutes after the primary (`50 14` then `27 15` UTC) plus a guard step that fast-forwards to the branch tip and stands the run down when `data/captures.jsonl` already holds today's `captured_at` — it asks the DATA, not the workflow's own run history, because a scheduled run is pinned to the SHA at trigger time. The normal cost is one cheap checkout; 15:27 is inside the drift this workflow has always tolerated (a July run fired at 16:01), so a rescued day is priced at essentially the geometry the σ/bias tables were fitted at. Never hand-dispatch a catch-up run at an arbitrary hour to fill a gap: the per-(city, lead) tables are fitted at the ~15:00 UTC capture geometry, and an off-hour run injects rows priced under a different geometry (and, late in the UTC day, lead-0/post rows for a day already partly resolved) into the λ and refit populations — strictly worse than the missing day.
- **Two venues, one pipeline:** `capture_prices` pulls both Polymarket and Kalshi into the same `WeatherMarketRow`. Kalshi MARKET DATA is fetched anonymously from the public production host (`config::kalshi_public_base_url`, api.elections.kalshi.com) — real prices, no creds — scanned per weather series (`WEATHER_SERIES` in `src/api/kalshi_history.rs`; an untargeted `/markets` scan never reaches them). The anonymous market list NULLS price fields, so the per-market public ORDERBOOK fills `best_bid`/`best_ask` and the mid replaces the last-trade fallback. Kalshi gotchas the parser encodes (each cost real calibration before the fix): the target day comes from the TICKER (`KXHIGHNY-26JUL04-…`) because close/expiration times are the morning AFTER; `greater`/`less` strikes are STRICT (floor 105 = "106° or above" ⇒ threshold 106); titles say "high temp", not "temperature". RSA-PSS signing (`KALSHI_API_KEY_ID` + `KALSHI_PRIVATE_KEY_PATH`/`_PEM`, `config::kalshi_base_url` = demo by default) is only for future TRADE endpoints (`has_trade_auth()`). Every row/capture carries a `source`; old captures default `"polymarket"`. Snapshots also store `best_bid`/`best_ask` (both venues) so the dashboard can price edge at EXECUTABLE prices — `decide()` fills BUYs at the ask and SELLs at the bid, falling back to the last trade only for legacy rows without book data. Fresh snapshots additionally carry LOG-ONLY research fields (nothing in the trading path reads them; older rows default None): venue attention proxies (`volume`/`volume_24h`/`open_interest`/`liquidity` — does hype money widen mispricing?), target-day smoke (`pm25_max`/`us_aqi_max` from Open-Meteo's air-quality API at city coords — hypothesis was that wildfire smoke suppresses daily highs and the blend only partly prices it; first look 2026-08-09: DEAD — heavy-smoke days (>55 µg/m³, n=20 of 208 deduped city-days) realized +0.53 °C ABOVE forecast, same sign as the general summer drift, r ≈ +0.03; no correction warranted, field stays for a bigger-sample recheck), and AI-model daily highs (`forecast_high_aifs`/`forecast_high_aigfs`, the `AI_LOG_CANDIDATES` in `open_meteo_fetcher.rs` — per logical model an ordered (endpoint, name) candidate list with an hourly-collapse fallback, because the July 19 capture proved single guessed names silently fail; the daemon prints which candidate served each model, or that all failed, once per run; fetched one model per request at the same coords the row was priced at. Slot 1 was GraphCast until 2026-07-22 — it never logged a value because NCEP discontinued GraphCastGFS/EAGLE in Dec 2025; NOAA's operational successor AIGFS, `ncep_aigfs025` on Open-Meteo since Jan 2026, replaced it and the never-populated `forecast_high_graphcast` field was dropped), and since 2026-07-23 ensemble member spreads (`ensemble_spread_ecmwf`/`ensemble_spread_gfs`: std-dev °C across ensemble members' daily highs for the target day, `ENSEMBLE_LOG_CANDIDATES` via the separate `ensemble-api` host, same candidate-list + per-run-diagnostic pattern; ≥8 members or the date is dropped — the DAY-SPECIFIC uncertainty candidate, because the pricing σ was a per-(city, lead) constant that priced locked-in and coin-flip days identically; the required gate — a spread→σ mapping fitted walk-forward that beats the constant-σ tables — was MET at the 2026-08-09 check, so unlike its list-mates this field is no longer log-only: the fetch moved into `StationPricer` and the stored spread is the spread the row was priced with — see station-aware pricing below). Since 2026-08-09 two μ-side LOG-ONLY fields ride along, the remaining sharpening candidates after the smoke dead-end: ensemble member MEANS (`ensemble_mean_ecmwf`/`_gfs`, same fetch as the spreads at zero marginal cost — ensemble means routinely beat deterministic runs at lead 1–2, so these face the same beat-the-blend RMSE gate as the AI means in `lambda_diagnostics.py` `ai_means`) and per-model blend member highs (`blend_model_highs`, BTreeMap keyed by `BLEND_MODELS` name — BTreeMap so the daily full-file rewrite stays byte-stable — at the row's resolution station, full target day, station rows only: the raw material for fitting per-city blend WEIGHTS walk-forward, which had nothing to fit while only the average survived the run). The AI models must beat `BLEND_MODELS` on accrued captures BEFORE entering the blend — changing the blend invalidates the fitted sigma/bias tables. Analysis scripts over accrued captures, each with a dated "First look" verdict in its docstring: `scripts/microstructure_lambda.py` (λ conditioned on book/attention microstructure — first look: Polymarket books wider than ~2¢ have NEGATIVE executable-price λ (−0.29), a live Filter-A/B candidate; Kalshi non-monotone, needs data) `scripts/fit_tail_distribution.py` (Student-t vs Normal residual tails, censoring-aware because off-ladder days resolve on open-ended markets and dropping them truncates exactly the tail being fitted — first look: t(ν≈2.5–3) wins the likelihood decisively but walk-forward bucket Brier by only ~0.5% with the gain attributable to scale not tail shape, so the Normal CDF stays), and `scripts/lambda_diagnostics.py` (why λ is ~0.35 and what would raise it — see **λ is a scoreboard** below).
- **λ is a scoreboard, not a knob** (`scripts/lambda_diagnostics.py`, first look 2026-07-26, 1864 resolved lead ≥ 1 rows). λ tracks the model's Brier edge over the market almost one-for-one by week: +0.027 edge → λ 0.85 (wk 06-29), −0.022 → λ 0.09 (wk 07-13), −0.003 → λ 0.42 (wk 07-20). It rises only when the model gets *sharper than the market*; nothing else moves it. Both pricing-side hypotheses are dead on this sample: the σ sweep is Brier-optimal at exactly c = 1.0 and widening σ LOWERS λ (0.305 → 0.192 at c = 2.0), and estimates are well calibrated in aggregate (model 0.2–0.3 realizes 0.257; through-origin slope 0.854); the 07-20 seasonal refit already fixed the bias (Kalshi weekly residual −0.80/−1.18 → −0.04 °C), and a further walk-forward bias correction moves Brier only 0.1026 → 0.1020 while LOWERING λ. What remains is heterogeneity, on an axis the strategy does not currently filter: **sub-10¢ markets carry negative λ on BOTH sides** (BUY −0.086 n=778, SELL −0.105 n=203) while everything ≥ 10¢ is healthy (BUY +0.363 n=219, SELL +0.540 n=664). That reframes "BUYs are worthless" — the dead segment is the TAIL (981 of 1864 rows), where the model's own Normal tail carries no information, not the buy side. Secondary axes: shape (temp_at_most +0.671 / temp_at_least +0.366 / temp_bucket +0.239) and city (kalshi/Miami +0.768, kalshi/Austin +0.750 vs kalshi/Chicago −0.250, polymarket/Istanbul −0.618). All of it is WITHIN venue, yet the default fit is per venue only (kalshi 0.341 vs polymarket 0.391) — averaging healthy and anti-signal segments together. **Segment-conditioned λ landed 2026-07-26 as the A/B candidate `--segment-lambda`** (`ShrinkageFit::observe_seg`/`lambda_seg`, band split at 10¢ via `lambda_segment`, fallback segment → venue → pooled → 1.0, venue lookups fold across segments so the default path is unchanged): it zeroes the bad segments by construction — negative segment slopes clamp to 0, an ADAPTIVE price floor — instead of needing the hand-picked `--min-price`. The walk-forward prototype (`scratchpad` script, results in the shrinkage.rs docs) lifted the out-of-sample calibration slope 0.674 → 0.701 and flipped flat-stake ROI −9.3% → +7.5% on the identical population; per-side λ is looked up with each side's own fill price (a BUY at the ask and a SELL at the bid can sit in different bands). The AXIS was chosen on this same sample, so it earns forward A/B rows before becoming the default. Of the two logged sharpening candidates, the AI means stay log-only (AIFS RMSE 2.23 °C vs the blend's 1.33 at the 08-09 look) — but ensemble spread, 67 usable rows at first look, reached 1108 and CLEARED its gate at the 2026-08-09 check (walk-forward σ = a·spread bucket Brier 0.0947 vs the constant tables' 0.0971 on the same 1038 rows, λ +0.347 vs 0.328 pooled; the loss is concentrated exactly where spread says it should be — the high-spread tercile scores Brier 0.1041 under constant σ): promoted into pricing, see station-aware pricing.
- **Station-aware pricing (how active temp markets are actually priced):** the two venues resolve on DIFFERENT truth variables at DIFFERENT stations, and `src/stations.rs` holds a verified table per venue (`station_for(city, source)`). Polymarket: **Wunderground daily-history max** — max of whole-degree METAR obs at the named airport, NOT the NWS CLI high (often 1°F higher) — traps: Denver→KBKF Buckley (not KDEN), London→EGLC City (not Heathrow), Dallas→KDAL Love (not DFW); reproduced 48/48 settled captures across 28 mapped cities incl. internationals (all °C). Four cities are deliberately UNMAPPED (legacy path): Hong Kong (resolves on the HK Observatory climate extract, one-decimal °C, no METAR), Moscow, Istanbul, Tel Aviv (non-Wunderground national sources). Seoul is mapped but honestly wide (σ≈3.4: Incheon is an island; the forecast grid cell is mostly sea). Kalshi: **NWS CLI daily max** (continuous sensor, ≥ ob-max by 0–2°F, so its `post` phase carries a fitted bias/σ instead of being exact) — traps: Kalshi Dallas→KDFW, NYC→Central Park, Houston→Hobby, Denver→KDEN; every row re-scored 402/402 settled 2026 markets (6,030 total). Each row has per-(city, lead k∈{0,1,2}) `sigma`/`bias` (°C) fitted Jan–Apr 2026 at the daemon's exact capture geometry (15:00 UTC ≈ the 9am launchd run — refit if the schedule hour changes). `capture_prices::StationPricer` prices per phase: local day over ⇒ ob-max (+ venue post bias/σ); day-of ⇒ max(running ob max from IEM `obhistory.json` — near-real-time; the bulk asos.py archive lags a day at some stations — remaining-hours live forecast at STATION coords); lead k ⇒ station-coords forecast + fitted bias/σ. Unmapped cities, precipitation, or failed fetches fall back to the legacy `evaluate_markets_with_forecast` path (downtown coords, σ=2.0). Refit constants from accrued captures (`forecast_high`/`forecast_sigma` stored per snapshot) as seasons drift. First seasonal refit landed 2026-07-20 (k=1,2 slots only; k=0/post untouched): realized highs recovered from winning bucket markets showed a venue-pooled summer over-forecast the winter fit couldn't see (−0.50 °C Polymarket / −0.98 °C Kalshi — a full 2 °F bucket) plus per-city empirical-Bayes deltas (largest: Kalshi LA −2.0 °C, July marine layer), σ rescaled ×1.32 PM / ×0.9 Kalshi; walk-forward validated +5% bucket Brier. **Second refit landed 2026-08-05** (k=1,2 again): that ×1.32 OVER-widened — post-refit z = (realized − forecast)/σ had sd 0.78 with 82% of days inside ±1σ vs the Normal's 68% — while the mean drifted back the other way as record-hot July outran constants fitted through 07-19 (realized − forecast by target week: −0.86 → +0.19 → +0.19 → +0.45). So it ADDS bias (venue mean +0.32 °C PM / +0.04 Kalshi, per-city EB-shrunk) and SHARPENS σ ×0.8 both venues; walk-forward +5.5% bucket Brier on 668 rows. ×0.8 is a deliberate HALF-STEP — unconstrained the fit wanted ×0.61/×0.68 for +7.3%, but σ sharpening is the overconfidence direction (cf. the `temp_predictive_sigma` bug) and 167 residual observations is thin for halving spread at once. **Third refit landed 2026-08-30, BIAS ONLY.** The eight `KXHIGHT*` Kalshi cities that entered the universe on 08-19 had never contributed to a refit and their Jan–Apr constants were pushing the wrong way in August: the fit adds **Vegas +0.90 °C, Washington +0.83, Boston +0.76, Seattle +0.53, Phoenix +0.46, Atlanta +0.37** (venue mean +0.35 Kalshi / −0.27 Polymarket, EB-shrunk per city, applied to `bias[1]`/`bias[2]` on BOTH tables; k=0 and post untouched as always). It also relieves the long-standing Kalshi LA overcorrection, −2.342 → −1.972. **The σ half was deliberately NOT applied, and that is measured rather than cautious:** walk-forward Brier is **+3.0% bias-only vs +2.9% with the σ rescale**, so the rescale contributes nothing; it is fitted on just 31 Polymarket / 25 Kalshi constant-σ rows (barely over the ≥20 gate) and has oscillated ×1.32 → ×0.8 → ×1.376 across three refits, while since the 08-09 ensemble-σ landing the constant σ table is mostly a fallback anyway. `scripts/refit_station_tables.py` reproduces the fit (pass `--since 2026-08-30` next time — the script's own default still reads 2026-08-05); its `--sigma-floor` (default 0.8) caps the per-refit sharpening step, and its `--since` must name the LAST TABLE CHANGE (default now 2026-08-05; keep it in step with each refit landing) — pooling rows priced under earlier constants mixes two regimes and the script's own walk-forward check correctly rejects the result (−2.8% vs +5.5%). New constants affect FUTURE captures only; stored `forecast_high`/`model_estimate` on existing rows are historical snapshots, so no past A/B number moves. **Dynamic σ landed 2026-08-09** (`backtesting::spread_sigma`): lead ≥ 1 STATION rows whose target day carries an ensemble spread price at σ = max(a·spread, 0.2 °C) instead of the constant slot. `a` is grid-fitted (0.4..3.0 step 0.1, Brier-minimizing, ≥40 rows) from resolved captures at each run's start by BOTH `capture_prices` and `kalshi_pilot` — walk-forward by construction, since resolved rows are strictly earlier than anything still being priced (a = 1.1 at landing; the Rust fit reproduces `lambda_diagnostics.py`'s population and optimum exactly, verified 1108/1108). Day-of/post phases, the legacy path, and spread-less rows keep their constants; μ and the fitted bias are untouched. Affected rows carry `sigma_source: "ensemble"` — treat 2026-08-09 as a σ-REGIME boundary: since 2026-08-17 `refit_station_tables.py` splits on it (ensemble-σ rows stay in the bias fit and walk-forward evaluation — bias-only there — but are excluded from the z-based σ rescale, which governs only the constant tables; `lambda_diagnostics.py`'s σ sweep likewise reports per-regime optima, which had already diverged at first look: constant rows c≈0.8, ensemble rows c≈1.2), and the σ half of the k=1,2 tables is now mostly a fallback (the bias half still applies to every row). ## Architecture

Rust port of a Python weather-market trading system. The Python original is archived verbatim under `archive/python-legacy/` with a mirrored module layout — consult it when a Rust port behaves unexpectedly or a feature looks missing.

**Pipeline (the core data flow, spanning many files):**

1. **Fetchers** (`src/data_pipeline/*_fetcher.rs`) — one struct per weather source, all exposing `fetch_location(key, start, end) -> Vec<WeatherRecord>`. Free sources (open-meteo, nws, noaa, awc) always run; API-keyed sources (owm, visual_crossing, weatherapi, tomorrow_io, accuweather) implement `is_available()` and are **silently skipped when their key is unset**. A failed/erroring fetch returns an empty `Vec`, never panics — degradation is by design.
2. **`MultiSourceAggregator`** (`multi_source_aggregator.rs`) — calls every fetcher, groups records by date, and averages each field across sources. A day is marked `is_validated` only when ≥2 sources agree. This is the single funnel all weather data flows through.
3. **`BayesianWeatherModel`** (`models/bayesian_model.rs`) — despite param names like `mcmc_draws`/`tune`, there is **no MCMC**. It uses closed-form conjugate updates: Normal–Normal for temperature, Beta–Bernoulli for precipitation occurrence. Predictions sample from the posterior with **fixed per-method seeds** (42/43/44/45) so results are deterministic.
4. **`MarketSimulator`** (`backtesting/market_simulator.rs`) — synthesizes markets from weather: computes rolling **climatological** probabilities and prices each market at that prob plus seeded Gaussian noise. Used only in simulated-backtest mode.
5. **`BacktestEngine`** (`backtesting/backtest_engine.rs`) — the orchestrator. Walk-forward: for each market date it trains a *fresh* model on the trailing `model_lookback_days` window (needs ≥14 records), computes `edge = estimate − price`, filters by `edge_threshold`, sizes with **fractional Kelly** (`kelly_fraction`, capped at `max_position_pct`), and books PnL. Two entry points: `run()` (simulated markets) and `run_with_real_markets()` (markets loaded from CSV/JSON via `RealMarketLoader`).
6. **`PerformanceAnalyzer`** (`backtesting/performance_metrics.rs`) — turns the trade log + portfolio curve into Sharpe, drawdown, return, etc.
7. **`market_estimate` / `evaluate_markets`** (`backtesting/backtest_engine.rs`) — a position-free path used by the dashboard and capture daemon. `market_estimate(model, market)` is the **single place market shapes are priced**: it routes on `market_type` (`temp_at_least`, `temp_at_most`, `temp_bucket`, plus legacy `temperature`/`precipitation`) and respects the market's `unit`. The `precipitation` shape is daily rain OCCURRENCE only — accumulation markets ("Will Seattle have between 2 and 2.5 inches of precipitation in July?") are dropped at parse time by `is_precip_accumulation` in `api/polymarket_history.rs`, because the model has no accumulation forecast and priced every one of them at the ~0.50 Beta prior, manufacturing a +55% edge that went 0-for-6 on settled trades. **The same prior leaked into the OCCURRENCE shape until 2026-09-01, by a different route.** `evaluate_markets_inner` builds a point-forecast model (`BayesianWeatherModel::default()` + `set_point_forecast`) for any city with a temperature forecast and then asks `market_estimate` every shape it holds — rain included. `set_point_forecast` writes only the temperature fields and sets `is_trained = true`; it never touches the Beta, which stays at its Default (1, 1). So `predict_precipitation_probability` answered from the untouched prior: 29 of 35 captured estimates were the SAME 0.496 across 11 climatically unrelated cities (Dubai, Phoenix, LA, Seattle, Hong Kong, Seoul...), scoring Brier 0.233 against the market's 0.066 on 33 resolved rows — 3.5× worse, and roughly what "always guess 0.5" scores. A 3¢ rain market therefore showed a +47% edge. Fixed by a `precip_trained` flag set only by `train_precipitation_model`: `predict_precipitation_probability` now errors without it, `market_estimate` maps that to None, and `capture_prices` still writes the row with `model_estimate: null` so the price history survives while nothing fabricated is tradeable. `is_trained` alone was never evidence the Beta had seen a rain observation. Existing captures keep their stored 0.496 — like every constants change, this affects FUTURE captures only. `evaluate_markets` walk-forward-trains a model per market and returns predicted-prob-vs-outcome rows for `CalibrationAnalyzer` (`models/calibration.rs`: Brier, ECE, reliability diagram).

**Live trading** (`src/api/`): `PolymarketClient` (defaults to paper mode unless real auth is passed) and `LiveTrader`, which wires the same `BayesianWeatherModel` + `MarketMaker` against live orderbooks. Separate from the backtest path.

## Conventions & gotchas

- **Temperature units cross boundaries.** `WeatherRecord` stores °C. Config thresholds and `SimulatedMarket` use °F. Conversions happen at the edges — `backtest_engine::get_model_estimate` converts the °F threshold to °C before calling the model; `market_simulator` converts stored °C to °F. NOAA raw values are in tenths and divided by 10 in `normalize_noaa_data`. Real bucket markets carry an explicit `unit` (`"F"`/`"C"`); `unit: None` means legacy °F (back-compat for old CSVs). Get a unit wrong here and backtests silently produce garbage.
- **Two posterior sigmas — pick the right one.** Probabilities for "will the high exceed / fall in X" markets must use `temp_predictive_sigma` (posterior-mean variance + day-to-day sample variance, ≈ the sample SD, ~8°C), **not** `temp_posterior_sigma` (standard error of the *mean*, which only sizes the mean credible band). Using the latter made the model wildly overconfident — that was the `c4d4304` fix. Honor this when adding any new market shape.
- **`src/cities.rs` is the single source of truth for cities.** `infer_city(title)` matches a market title to a canonical key; `coords(key)` gives lat/lon for fetching. Add a city as one `City` row (key + lowercase title patterns + coords) so title-parsing and weather-fetching can't drift apart.
- **Config is functions, not a loaded struct.** `src/config.rs` exposes `bayesian_model_params()`, `backtest_params()`, `initial_capital()`, etc. Env-backed accessors each call `dotenvy::dotenv()` and fall back to a hardcoded default — there is no global config object.
- **Determinism is load-bearing.** Every RNG is a seeded `StdRng`. Tests and backtests rely on this; don't introduce `thread_rng()` or unseeded randomness in the model/sim/backtest paths.
- **Blocking vs async split.** Weather fetchers use `reqwest::blocking`. Only the Polymarket history downloader (`api/polymarket_history.rs`) is async (`reqwest` + `tokio`); its bin is `#[tokio::main]`. Don't call blocking fetchers from an async context.
- **CLI args are parsed by hand** (no `clap`): a `--key value` loop into a `HashMap`. Match that pattern when adding flags to a bin.
- Errors that cross module boundaries use `thiserror` enums (`RealMarketLoadError`, `PolymarketHistoryError`); internal model/training errors are plain `Result<_, String>`.
